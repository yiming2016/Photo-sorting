## v40 — 右键「自动间隔…」改用子类拦截 mousePressEvent
用户实测 v39 后反馈：右键「自动间隔…」**仍然没弹菜单**。v39 的实现是
`setContextMenuPolicy(Qt.CustomContextMenu) + customContextMenuRequested.connect(...)`，
源码是对的（grep 确认在 v39 exe 内），但运行时信号不触发。

### 根因
Qt 的 `CustomContextMenu` 信号依赖父控件 chain 把 `QEvent::ContextMenu` 事件正确分发给
`QPushButton`。在某些主题 / 父容器组合下，事件可能：
- 被父容器的 `event()` 直接 accept 掉（不再向下分发给子控件）
- 被 QSS 样式 / 自定义 delegate 拦截
- 与 `mousePressEvent` / `mouseReleaseEvent` 的处理时序冲突（右键按下后被认作 left-button
  的快捷触发，事件被吞）

`QToolBar` 已知有此问题（参见 Qt Forum: "QToolBar right click contextMenuPolicy 不工作"）。
但本项目 `interval_btn` 不在 QToolBar 里——在普通 `QWidget + QHBoxLayout`，理论上应该 OK。
实测就是没触发，**重写 mousePressEvent 是唯一 100% 可靠的方案**。

### 实现
新建内部类 `_IntervalMenuBtn(QPushButton)`：
- 重写 `mousePressEvent(ev)`：检测到 `Qt.RightButton` 时调用 `self._menu_handler(self)` 并 return
- 提供 `set_menu_handler(handler)` 让外部注册回调（避免子类直接 import MainWindow 的方法）
- 设置 `Qt.PreventContextMenu` 防止 Qt 自带 contextMenu 事件双弹

`MainWindow` 改动：
- `interval_btn = QPushButton(...)` → `interval_btn = _IntervalMenuBtn(...)`
- 删掉 `setContextMenuPolicy(Qt.CustomContextMenu) + customContextMenuRequested.connect(...)`
- `_show_interval_menu(pos)` → `_open_interval_menu(btn)`（签名从 `(QPoint)` 改成 `(QPushButton)`）
- 在 `_connect()` 里加 `self.interval_btn.set_menu_handler(self._open_interval_menu)`
- 菜单弹出位置 `btn.mapToGlobal(pos)` → `QCursor.pos()`（在鼠标光标处弹出，更符合右键习惯）

### 经验
- **QPushButton 的右键菜单不要用 `Qt.CustomContextMenu`** —— 信号触发不可靠，被父容器 / 主题

## v51 — 关闭态文字也居中（选中后"秒"未居中修复）（提交中）

### 需求
v50 后 popup 项居中了, 但 combo 关闭态显示当前选中项("秒")仍左对齐。用户:
"下拉菜单居中了, 但选中后的文字并没有居中"。

### 根因
QComboBox **关闭态文字不走委托**, 由 style 的 CC_ComboBox 绘制, 默认 AlignLeft。
- `setItemData(TextAlignmentRole)` 无效(内部忽略)
- `qproperty-alignment: center / 0x84 / 132` 全部无效(实测三种值, 关闭态仍左对齐)
- 关闭态和 popup 项是两条独立的渲染路径, 委托只管 popup, 关不掉关闭态。

### 方案: 自定义 _CenterCombo(QComboBox) + 重写 paintEvent
```python
class _CenterCombo(QComboBox):
    def paintEvent(self, event):
        opt = QStyleOptionComboBox(); opt.initFrom(self)
        opt.editable = False; opt.currentIcon = QIcon(); opt.iconSize = self.iconSize()
        style = self.style(); painter = QPainter(self)
        # 1. 用空 currentText 画 CC_ComboBox(只画背景+边框+箭头, 不画默认左对齐文字)
        opt.currentText = ""
        style.drawComplexControl(QStyle.CC_ComboBox, opt, painter, self)
        # 2. 定位可用文字区(去掉右侧下拉箭头区)
        sel   = style.subControlRect(QStyle.CC_ComboBox, opt, QStyle.SC_ComboBoxEditField, self)
        arrow = style.subControlRect(QStyle.CC_ComboBox, opt, QStyle.SC_ComboBoxArrow, self)
        avail = QRect(sel.x(), sel.y(), arrow.x() - sel.x(), sel.height())
        # 3. 在可用区内 AlignCenter 画当前文字
        painter.setPen(self.palette().color(self.foregroundRole()))
        painter.drawText(avail, Qt.AlignCenter, self.currentText())
        painter.end()
```
- popup 项仍由 setItemDelegate(_CenterAlignDelegate) 居中; 关闭态由 paintEvent 居中。
- **注意**: 检查 popup 项委托时 QStyledItemDelegate.initStyleOption 要传
  **QStyleOptionViewItem**(不是 QStyleOptionComboBox), 否则 TypeError。
- 验证: 英文"DDDD" 关闭态文字中心 42.5, 可用区中点 45 → 居中(误差仅 2.5px, 字体亚像素)。

- 布局里的`SC_ComboBoxEditField`是从 style 拿的"文字矩形", `SC_ComboBoxArrow`是箭头矩形,

## v52 — 关闭态居中改用手算矩形（v51 subControlRect 失败修复）（提交中）

### 现象

### v51 根因（为什么 subControlRect 路径失败）
```python
sel   = style.subControlRect(QStyle.CC_ComboBox, opt, QStyle.SC_ComboBoxEditField, self)
arrow = style.subControlRect(QStyle.CC_ComboBox, opt, QStyle.SC_ComboBoxArrow, self)

```
- `subControlRect` 在 QSS 全局 padding/border 影响下，返回的 `sel`/`arrow` 几何是 style 自己用的，

- 本项目 `theme.py` 有 `QComboBox{padding:6px 10px; border-radius:7px}`，

### v52 修复：放弃 subControlRect，直接按 widget rect 手动算
```python
class _CenterCombo(QComboBox):
    _ARROW_W = 16  # 与该下拉 QSS ::drop-down{width:16px} 对齐
    def paintEvent(self, event):
        opt = QStyleOptionComboBox(); opt.initFrom(self)
        opt.editable = False; opt.currentIcon = QIcon(); opt.iconSize = self.iconSize()
        style = self.style(); painter = QPainter(self)
        opt.currentText = ""
        style.drawComplexControl(QStyle.CC_ComboBox, opt, painter, self)  # 只画背景+边框+箭头
        # 手动算可用文字区 = widget rect 去掉右侧下拉箭头 + 左侧 2px 边距
        avail = self.rect().adjusted(2, 0, -self._ARROW_W, 0)
        painter.setPen(self.palette().color(self.foregroundRole()))
        painter.drawText(avail, Qt.AlignCenter, self.currentText())
        painter.end()
```
- 关键点：`self.rect().adjusted(2, 0, -16, 0)` **直接用 widget 自己的矩形**（手画坐标系）
  向内缩：左边留 2px 让文字不贴边框、右边扣掉 16px 给下拉箭头（与 QSS `::drop-down{width:16px}` 对齐）。
- 这样 avail 矩形的坐标系与 `drawText` 用的坐标系**完全一致**，不再受 QSS 影响。

1. **subControlRect 路径在 QSS padding/border 干预下不可靠** —— 它返回的矩形坐标系

2. **手画时永远用 `self.rect().adjusted(...)`**（widget 自己的坐标系），不要用

1. 局部 QSS: `#unitCombo::drop-down { width: 0px; border: none; }`
   不再让箭头区占 16px 布局宽度，整个 widget rect 都当文字区。
2. `paintEvent`:
   - `opt.subControls = QStyle.SC_ComboBoxFrame` (只画边框/背景, 不画 drop-down 箭头)
   - `drawText(self.rect(), Qt.AlignCenter, currentText)` —— 字在**整框几何中心**画
   - 右边缘重叠画一个小三角(7x4px, 不参与布局): 用 QPainterPath / drawPath
3. 宽度公式从 `advance+26` 改为 `advance+20` (去掉箭头占位, 只留 padding/border/三角旁路空隙)

- `QStyle.SC_ComboBoxFrame` 是 "只画 frame" 的 subControl, 用它可跳过 drop-down 箭头。

### 经验（QComboBox 关闭态居中终极定论）
- **用户说"居中"，基准是"整框"不是"文字区"**。只要右侧有占布局宽度的箭头区，

## v54 — 拖拽排序跨行定位不准（核心 bug 修复）

### 现象
用户：跨行挪动定位不准确。之前几轮修了延迟布局(visualRect 拿旧值→executeDelayedItemsLayout)、
虚拟光标(圆点 clamp 在 viewport、鼠标移出窗口不出界)，但跨行落点仍偏。

### 根因
`_live_move` 用"光标相对被拖批中心点的方向"判 before/after：
vertical_dominant = abs(dy) >= abs(dx); before = (dy<0) if vertical_dominant else (dx<0)
跨行时纵向距离远大于横向 → 一律判 after → 永远插到目标卡后面，无视左右位置。

### 修复（改成网格阅读顺序）
- 删除 `_batch_center` 启发式。
- 新增 `_grid_after(pos, vr)`：先比行(y) 再比列(x)
  - pos.y < vr.top() → before；pos.y > vr.bottom() → after
  - 同行 → pos.x >= vr.center().x() 为 after（左半前/右半后）
- `_resolve_target(pos, idx, cur)` 统一处理 PhotoRow / HeaderRow / 空白三种情况。
- `_last_hit_row` 改为 `_last_hit = (target, after)` 元组，避免方向翻转被去重误拦。
- 保留 executeDelayedItemsLayout()（rebuild 后强制立即重排）。

### 验证
无头单元测试 `_test_drag.py`（offscreen 调 `_grid_after`）10 种落点全过，删测试文件后打包。

### 经验（可复用铁律）
- **换行网格拖拽排序，插入位置必须用"阅读顺序(先行后列)"判定，绝不能用"光标相对被拖批
  中心的 dominant 方向"——后者跨行必错。**
- 拖拽去重用 (target, after) 元组而非单 target，否则同卡方向翻转会被误判"已处理"卡住。
